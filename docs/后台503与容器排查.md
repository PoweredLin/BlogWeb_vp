# 后台加载与重复容器处理（2026-11-07）

## 本次修复

后端原先设置 Uvicorn 并发上限 32，后台入口含约 40 个预加载链接。Uvicorn 达到连接或任务限制会直接返回 503；串行 curl 全部成功并不能证明浏览器并发加载也成功。查看 `docker compose logs --tail=200 space` 是否出现 `Exceeded concurrency limit` 可以核对现场。不是所有 503 都由此引起，应结合日志和响应体判断。

此外，响应中间件使用 `/admin` 前缀匹配，把 `/admin-app/assets/` 的长期缓存也覆盖成 no-store。修复后带 hash 的 JS/CSS 可公开缓存一年；管理 HTML 和所有 API 继续 no-store，私人数据不会缓存到 CDN。公开构建资源跳过会话数据库查询，私人上传仍保持原来的鉴权。

并发上限调整为 128、keep-alive 为 2 秒；后台禁用 HTML modulepreload，静态 import 仍是必需依赖，并没有删除所有共享组件或保证首屏不下载组件库。后续是否拆分图表和组件库，应以冷启动请求及体积测量为依据。不能把整个构建目录 10 MB 当作首屏实际下载量。

## 两个容器来自哪里

镜像 `lin-notebook:10` 可以创建任意多个容器。截图显示 `linbookV10` 与 `lin-notebook-space-1` 都引用了它；后者符合本项目 Compose 命名，前者可能由宝塔“创建容器”另行建立，需检查标签才能确认。镜像列表不代表两者都在运行。

在服务器执行只读检查（不会显示容器环境密钥）：

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker inspect linbookV10 lin-notebook-space-1 --format '{{.Name}} state={{.State.Status}} compose={{index .Config.Labels "com.docker.compose.project"}} service={{index .Config.Labels "com.docker.compose.service"}}'
docker inspect linbookV10 lin-notebook-space-1 --format '{{.Name}}{{range .Mounts}}{{println .Source "->" .Destination}}{{end}}'
```

只保留一个正式写入实例，统一由 `/www/wwwroot/lin-notebook-v10/compose.yaml` 管理。先确认 Compose 容器挂载的是已有的正式 data；如果额外容器曾接收过写入，先保留其数据快照，不能直接删除或覆盖。

确认后保持 `linbookV10` 停止，启动 Compose 实例：

```bash
cd /www/wwwroot/lin-notebook-v10
docker compose up -d --no-build space
docker compose ps
docker compose port space 4317
```

宿主机端口应继续为 4318，宝塔代理仍指向 4318；容器内端口为 4317。不要在宝塔镜像页再次点击“创建容器”，也不要删除镜像、data 或任何卷。`vaultwarden` 为其他项目，不做操作。额外容器保持停止即可，删除并不是修复后台慢的必要步骤。

## 部署补丁

本次只更新代码与构建，不搬数据库、不初始化账号。

1. 记录现有提交、镜像 ID，并保留旧镜像标签，按既有流程备份数据和配置。
2. 进入 v10 目录，检查 `git status --short`。服务器对 Compose 的 4318 修改要保留，不使用强制 reset。
3. 获取修复代码，构建镜像，然后用 Compose 重建唯一正式服务。

```bash
git pull --ff-only origin main
docker compose build space
docker compose up -d --no-build --force-recreate space
docker compose ps
docker compose logs --tail=100 space
```

若 pull 报本地 Compose 冲突，先保存差异再合并，端口最终必须保留 `127.0.0.1:4318:4317`。重建不需要 `--no-cache`；构建会识别改动。只有确认相关源码变化未进入构建时才调查缓存或目录问题。

升级后从 Network 复制本次构建的真实 `/admin-app/assets/…js` URL，检查本地及公网响应应为 200，Cache-Control 应含 `public,max-age=31536000,immutable`，而 `/admin/room` 仍为 `no-store`。Cloudflare 的自定义规则若主动绕过缓存，需另外核对。多次打开后台时应复用静态资源；若仍 503，保留失败响应体与对应时间日志，不再反复全量重建。
