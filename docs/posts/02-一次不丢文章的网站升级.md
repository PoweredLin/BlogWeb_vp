# 一次不丢文章的网站升级：从本地验证到 Docker 发布

网站刚开始运行时，重新上传一份代码似乎就算完成部署。等到里面已经有文章、图片和自己的使用记录，再做升级，关注点就变了。

页面能不能打开只是第一步。原来的文章还在吗？图片路径是否正确？账号能不能登录？看到的到底是新服务，还是代理仍指向旧进程？这些问题需要在升级前就想清楚。

这篇记录林间笔记本次升级采用的方法。它是一份发布前的技术整理，不把尚未执行的云端验收写成已经完成。

## 先把代码和数据分开

代码可以放进 Git，用提交记录追踪变化；文章、账号、图片和邮箱凭据则是运行数据，不能跟着一次代码更新被覆盖。

当前服务采用 Vue 3、FastAPI 与 SQLite，通过 Docker 运行。数据库和上传图片保存在容器外的持久化目录，环境配置独立保存。换镜像时，换的是程序，不是把本地演示数据库带上服务器。

尤其要保留邮件加密密钥。授权码虽然已经加密存入数据库，解密它的密钥仍来自部署环境。只备份数据库、不保存密钥，恢复出来的邮件设置也可能无法继续使用。

## 记录现场，比记住默认端口更重要

同一台服务器可能留着以前的 Node 服务，也可能有另一个 Docker 容器。新容器显示 healthy，并不代表浏览器访问到的就是它。

我会先核对实际监听端口、容器映射、数据挂载和 Nginx 的代理目标，再检查 `/healthz`。健康接口返回的版本和服务日志一起看，才能确认请求走到了预期程序。

这次保留了一个特别容易忽略的细节：反向代理传递真实的站点 Host，而不是固定写成回环地址。应用会校验域名，代理头错误时，后端即使运行正常也会拒绝请求。

## 构建时不断站，切换时先停写

依赖安装和镜像构建可以先做，不必为了等待下载让网站提前停机。

真正切换之前，再停止旧服务的写入并做完整备份。SQLite 可以使用在线备份接口生成一致性数据库，但数据库和图片还需要在同一停写窗口内保存，避免出现文章已经备份、对应图片却还没复制的情况。

候选测试使用生产数据的副本。它和正式站必须分开数据目录、端口与网络；仅仅换个端口，仍然挂载同一份数据库，并不叫隔离。副本中的邮件计划和自动化也要暂停，免得测试时把周报真的发出去。

## 验收要顺着实际使用路径走

我把验收分成三层：

1. 程序层：构建、接口、权限、导入校验与数据库完整性。
2. 页面层：阅读、封面、海报墙、主题、手机布局与失败提示。
3. 部署层：容器健康、反向代理、HTTPS、重启持久性和真实邮件投递。

本地测试能覆盖前两层的一部分，却不能代替服务器上的第三层。模拟 SMTP 测试通过，不说明服务商授权码和出站网络已经可用；页脚显示服务正常，也只说明最近一次应用与数据库检查成功。

## 回滚是升级的一部分

旧镜像、旧配置和升级前快照都要留到验收结束。

如果新版本已经接收了文章或评论，再回滚就不能直接用旧快照覆盖当前数据。先停写并保存新数据，再决定如何导出、合并或恢复。否则“恢复服务”可能顺手丢掉刚刚发布的内容。

这套过程并不复杂，也不需要把个人网站做成企业平台。它只是把几个容易混在一起的动作分开：构建代码、保存数据、验证候选、切换流量，以及确认可以恢复。

对个人小站来说，可靠的升级意味着：折腾完一圈，原来的故事还在，下一篇也能安心写下去。
